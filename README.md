# Cybersecurity Log Analyzer

> **Personal project** · Python (standard library only) · pytest

A command-line tool that parses **SSH authentication logs** and **web server access logs**
and flags suspicious activity: brute-force logins, password spraying, possible account
compromise, web scanners, and common injection attempts. Every alert is produced by a
simple, explainable rule (thresholds, sliding windows, signatures) so it can be traced
back to the raw log lines.

It is a learning project meant to show how detection logic works. It is not a replacement
for a SIEM or an IDS.

## What it detects

| Rule | Logic | Severity |
|---|---|---|
| `ssh_success_after_failures` | ≥5 failures from an IP within 10 min, then a successful login from the same IP | critical |
| `ssh_bruteforce` | ≥5 failed logins from one IP inside a 10-minute sliding window (≥20 → high) | medium / high |
| `ssh_password_spraying` | ≥5 distinct usernames from one IP, averaging ≤3 attempts per username | high |
| `web_scanning` | ≥15 HTTP 403/404 responses to one IP inside 5 minutes | medium |
| `web_sensitive_path_probe` | requests for `/.env`, `/.git/`, `/wp-login.php`, `/phpmyadmin`, `/admin`, … (high if the server answered 200) | medium / high |
| `web_sql_injection`, `web_xss`, `web_path_traversal`, `web_command_injection` | regex signatures on the URL-decoded request (decoded twice, to catch double encoding) | high |
| `web_scanner_user_agent` | User-Agent of known tools (sqlmap, Nikto, Nmap, Masscan, …) | high |

Rules overlap on purpose: a brute-forcer that finally gets in produces both a `medium`
brute-force alert and a `critical` success-after-failures alert, and the critical one
sorts to the top.

## Quick start

```bash
# Standard library only (tested on Python 3.13); no packages needed to run the tool
python samples/generate_sample_logs.py          # creates samples/auth.log and samples/access.log
python -m loganalyzer --auth samples/auth.log --web samples/access.log --year 2026
```

`--year` is needed because syslog timestamps don't contain one (default: current year).

### Options

```bash
python -m loganalyzer --auth /var/log/auth.log --year 2026      # one source is enough
python -m loganalyzer --web access.log --format json --output report.json
python -m loganalyzer --auth auth.log --ssh-fail-count 10 --ssh-window-min 5   # tune thresholds
python -m loganalyzer --auth auth.log --fail-on high            # exit code 2 if any finding >= high (cron/CI)
```

## About the sample data

The sample logs are **synthetic**, generated by `samples/generate_sample_logs.py` with a fixed
random seed. They contain normal staff logins (some with typos) and visitor traffic (some
harmless 404s), plus five web attacks and three SSH attacks I seeded deliberately. All IP
addresses are from the reserved documentation ranges (RFC 5737), so no real hosts appear.

This makes the tests meaningful in both directions: every seeded attack must be found, and
none of the normal users may be flagged.

## Tests

```bash
pip install pytest
pytest -v
```

39 tests: parsers (field extraction, timezone conversion, skipped-line counting), each
rule at, below and above its threshold, **false-positive guards** (a single typo then
success, slow attempts spread beyond the window, a brute-forcer that is not password
spraying, benign URLs containing words like "union"), and end-to-end CLI runs including
JSON structure and exit codes. A test also regenerates the sample logs in a fresh process
and checks that they match the committed files byte for byte.

## Project layout

```
loganalyzer/
  parsers.py      regex parsers -> AuthEvent / WebEvent (bad lines are counted, never fatal)
  detectors.py    one function per rule + Thresholds + run_all()
  report.py       text and JSON output
  cli.py          argparse interface and exit codes
samples/          deterministic sample-log generator and its output
tests/
```

## Limitations

- **Heuristics, not certainty.** Thresholds trade missed attacks against noise; tune them to
  your environment. Many users behind one NAT address can look like a single noisy IP.
- **Signatures are easy to evade** (unusual encodings, slow-and-low scanning). They catch
  commodity tooling, not a careful attacker.
- **Per-IP view only.** It doesn't correlate across IPs (a distributed brute force from
  many addresses will fall under every per-IP threshold).
- **Whole files are read into memory,** which is fine for a day of logs on one server but
  not for very large archives.
- **Two formats only:** OpenSSH `sshd` lines and Apache/Nginx combined logs. Adding a format
  means adding a parser that returns the same event types.

## Ideas for next steps

IP reputation / GeoIP enrichment, streaming (tail -f) mode, per-user baselines for
"impossible travel" style detection, and export to a SIEM-friendly format.
